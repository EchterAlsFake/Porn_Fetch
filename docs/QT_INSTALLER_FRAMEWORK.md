# Qt Installer Framework handoff for the 3.9 beta

This describes the current 3.9 source tree, not the published 3.8 GPL build.
The GitHub build workflow now creates IFW installers and repositories alongside
the standalone builds. Repository deployment is a separate, explicitly selected
workflow action. Manual installation and update testing is still needed before
an installer is offered to beta users.

## How the pieces fit together

1. `pyside6-deploy` builds the desktop application for one OS and architecture.
2. `packaging/generate_repository.py` stages that build, PocketBase, package
   metadata, and the installer configuration.
3. Qt IFW's `repogen` turns the staged package into a repository containing
   `Updates.xml`, component metadata, and versioned archives.
4. Qt IFW's `binarycreator --hybrid` makes an installer containing the initial
   app. It also records the remote repository URL for the maintenance tool.
5. After installation, the app can start `maintenancetool --updater`. The
   maintenance tool reads the remote repository, compares component versions,
   downloads the new archives, and installs them.

The server does **not** need to implement the installer protocol. It only needs
to serve the exact files generated by `repogen` over HTTPS, preserving paths
and bytes. Licensing is separate: the sandbox checkout and license validation
remain on the existing website and licensing service. The Arch Linux host now
serves these files with Caddy from `/srv/pornfetch-downloads/public/repo`.

## Repository URL and server work

The template at `packaging/installer/config/config.xml.template` currently
embeds this URL in new installers:

```text
https://api.pornfetch.to/repo/<os>_<architecture>
```

The CI job currently generates `windows_amd64`, `linux_amd64`,
`darwin_amd64`, and `darwin_arm64`. The server also has initialized
`linux_arm64` and `windows_arm64` directories, but the current CI does not
publish packages for those two. Linux and Windows ARM64 still have
standalone GUI builds but no IFW installer job because Qt's published IFW tools
for those runners are not yet wired into this pipeline. The server must host a
separate generated repository at each URL you actually ship. For example,
`linux_amd64/Updates.xml` must be available at:

```text
https://api.pornfetch.to/repo/linux_amd64/Updates.xml
```

Server tasks:

- Serve `Updates.xml`, metadata, and archives as ordinary static files under
  each architecture directory. Preserve the directory tree from `repogen`.
- Use HTTPS and allow normal GET requests for the metadata and archives. Avoid
  routing those paths through the license API or a page that returns HTML.
- Upload all new component archives and metadata **before** replacing the live
  `Updates.xml`. Publish that file last so clients cannot see an update whose
  archives are still missing. Keep the previous repository available until the
  replacement is complete.
- Keep this beta repository distinct from any future stable channel if stable
  users should not receive beta updates. A different channel URL requires a
  different installer config or a deliberate repository migration.
- Check that an installed beta can fetch the URL and update without relying
  on a developer checkout or local files.

`packaging/generate_repository.py` only writes local output. The workflow's
`deploy-repositories` job downloads the generated repository artifacts and
uploads them over SSH on a manual workflow run when **Deploy Qt IFW
repositories** or **Publish artifacts as a GitHub Release** is selected,
together with **Legal review complete**. A release waits for successful
repository deployment. Tag pushes build installers but do not deploy them.

Configure the GitHub `beta` environment before enabling deployment:

| Name | Type | Value |
| --- | --- | --- |
| `IFW_DEPLOY_HOST` | Variable | SSH address for the Arch Linux host, reachable from the GitHub runner |
| `IFW_DEPLOY_USER` | Variable | `pornfetch-deploy` |
| `IFW_DEPLOY_ROOT` | Variable | `/srv/pornfetch-downloads/public/repo` |
| `IFW_DEPLOY_SSH_KEY` | Secret | Contents of the private deployment key generated on the server |
| `IFW_DEPLOY_KNOWN_HOSTS` | Secret | Verified `ssh-ed25519` host key line, using the exact configured SSH host |

The server agent reports that Caddy serves this tree at both
`https://api.pornfetch.to/repo/` and
`https://downloads.pornfetch.to/repo/`. The installers use the API hostname.
The canonical deployment root is `/srv/pornfetch-downloads/public/repo`, so
`https://api.pornfetch.to/repo/linux_amd64/Updates.xml` maps to
`/srv/pornfetch-downloads/public/repo/linux_amd64/Updates.xml`. The server
needs `rsync` and `ssh`. The current deploy job uploads archives and metadata
without deleting old files, then replaces each `Updates.xml` last. This is
static file hosting, separate from the crypto sandbox and license API.
As checked on 28 September 2026, the live `linux_amd64/Updates.xml` is an
empty `<Updates>` document; a successful HTTP response alone does not mean a
beta package has been published.

The `pornfetch-deploy` account has full write access to the public repository
root. The IFW deploy script writes there directly. The server's separate
`/srv/pornfetch-downloads/incoming` directory and `pornfetch-activate` command
are not part of this repository upload.

GitHub-hosted runners must also be able to reach the chosen SSH host. A private
LAN or WireGuard IP works only if the runner is connected to that network. The
`IFW_DEPLOY_KNOWN_HOSTS` entry must name the same host or IP configured in
`IFW_DEPLOY_HOST` and contain its verified public host key.

## Building a repository and installer

CI downloads pinned Qt Installer Framework 4.11 archives and verifies their
SHA-256 hashes before extracting them. It stages the existing GUI build and
PocketBase, then runs `repogen` and `binarycreator --hybrid`. For a local build,
install IFW so those commands are on `PATH`, and run the generator with a folder
containing the compiled app:

```bash
python packaging/generate_repository.py \
  --dist-dir /path/to/PornFetch.dist \
  --platform linux --arch x64 \
  --pocketbase-binary /path/to/pocketbase \
  --output-repo /path/to/output/linux_amd64 \
  --output-installer /path/to/output/PornFetch-linux-x64-installer
```

The `--dist-dir` value must be a **directory** with the executable and all
files the compiled application needs. CI copies its onefile executable into
that directory under the installed name expected by the package script. The
PocketBase binary must match the target platform. The script stages a single
core component named `com.echteralsfake.pornfetch`; keep that ID stable across
updates.

CI uses `3.9.<GitHub run number>` for the IFW component version, so successive
workflow runs can produce newer updates even while the application's displayed
version remains 3.9. For a local build, pass a higher `--version` than the one
already deployed. Upload the generated repository before telling users an
update is available. The maintenance tool compares component versions, so an
unchanged version will not appear as a newer update.

## Checks before distribution

- Inspect `Updates.xml` and confirm that it names the expected component and
  new version.
- Confirm the repository URL returns that XML and every referenced archive.
- Install from the hybrid installer on a clean machine and confirm the app,
  PocketBase, shortcuts, and maintenance tool work.
- Publish a second version to the same channel and verify both the app's update
  button and `maintenancetool check-updates` followed by an update.
- Confirm user data and license state remain available after an update.

These are manual release checks. The current automated tests cover parts of
the update orchestration but do not establish that a generated installer or
deployed repository works on Windows, Linux, or macOS.

## Commercial entitlement integration

The application discovers `release.json` in each platform repository. This is TUF
Targets metadata signed by the existing release targets key, binding the version,
immutable release timestamp, platform, and every repository file hash. The deployment
workflow signs it with `packaging/sign_desktop_release.py` and publishes it last.

Before launching IFW, Porn Fetch validates the license, checks the signed release
date, downloads and verifies the complete repository, and uses
`--set-temp-repository file:///...` so IFW sees only the verified release. Legacy
unsigned discovery is informational and cannot enable automatic installation.
See [licensing architecture](LICENSING_ARCHITECTURE.md) for release requirements.
